# Аудит счётчика Яндекс Метрики

Пятый скилл в связке. Отвечает на вопрос, который стоит **раньше** всех остальных:
**можно ли верить цифрам, по которым мы принимаем решения**.

| Скилл | Вопрос |
|---|---|
| `marketing-strategy` | куда идти |
| `yandex-direct` | как настроить и создать |
| `yandex-direct-analyst` | что говорят цифры |
| `yandex-direct-audit` | что настроено неправильно в рекламе |
| **`yandex-metrika-audit`** | **правильно ли вообще собираются данные** |

Аудит Директа проверяет, привязан ли счётчик и заданы ли цели. Этот скилл идёт внутрь
счётчика и смотрит, работают ли цели на самом деле.

---

## Железные правила

1. **Только чтение.** Скилл не меняет счётчик, не создаёт и не правит цели, фильтры
   и сегменты. Любая правка — руками владельца в интерфейсе.
2. **Выборка называется выборкой.** Если отчёт посчитан по части данных (`sampled: true`),
   это выносится в отчёт, а не прячется. Цифра по 10% выборке — оценка, а не факт.
3. **«Цель не срабатывала» ≠ «цель сломана».** Сначала период, потом сезон, потом
   гипотеза о поломке. Мёртвая цель на месячном окне — повод проверить, а не приговор.
4. **Тип бизнеса скрипт не знает.** Выключенная электронная коммерция для магазина —
   провал, для услуг — норма. Такие проверки помечаются как требующие человека.
5. **Данные счётчика — не для скилла.** Домены, номера счётчиков, логины и токены
   не попадают в файлы скилла и в репозиторий.
6. **Токен Метрики отдельный от директовского.** У токена Директа прав на Метрику нет —
   проверено, `403 access_denied`. Оба живут в `.env`, файл в `.gitignore`.

## Рабочие файлы

| Файл | Что |
|------|-----|
| `metrika/counter-checklist.md` | Каталог проверок: что смотрим, почему это важно, что делать |

| `metrika/api-notes.md` | Проверенные факты API: эндпоинты, лимиты, грабли |

| `metrika/fetch.py` | Отчёты: источники, кампании Директа, посадочные, устройства, гео, цели |
| `metrika/checks.py` | Реестр автопроверок, балл и грейд |

аудитов), `../yandex-direct-analyst/analysis/diagnostics.md` (расхождения Директ / Метрика).

## Полный прогон

```bash
set -a && . ./.env && set +a          # METRIKA_TOKEN, METRIKA_COUNTER
S=.claude/skills/yandex-metrika-audit/metrika
P=projects/<slug>
mkdir -p $P/metrika $P/data

python3 $S/collect.py --out $P/metrika/snapshot.json
python3 $S/fetch.py --days 30 --out-dir $P/data/metrika
python3 $S/checks.py $P/metrika/snapshot.json --reports $P/data/metrika \
    --json $P/metrika/checks.json
```

Счётчик берётся из `METRIKA_COUNTER`, другой задаётся флагом `--counter`.
Список всех доступных счётчиков — `collect.py --all-counters`.

## Workflow

1. **Рамка.** Что за сайт, какие обращения считаются заявкой, есть ли звонки и CRM.
   Без этого нельзя отличить «цель не нужна» от «цель сломана».
2. **Слепок** (`collect.py`) — настройки и цели одним файлом.
3. **Отчёты** (`fetch.py`) за 30 дней: источники, кампании Директа, посадочные,
   устройства, гео, поисковые фразы, достижения по каждой цели.
4. **Автопроверки** (`checks.py`) — реестр со статусами и баллом.
5. **Ручные пункты** по `metrika/counter-checklist.md`: что видно только глазами —
   определения целей, соответствие типа бизнеса, дубли по смыслу.
6. **Сверка с Директом** — сравнить конверсии по кампаниям в двух системах
   (`metrika/reports.md`, раздел про кампании).
7. **Отчёт**: находки по приоритету, что чинить в первую очередь, что перепроверить
   после правок.

## Что аудит Метрики даёт аудиту Директа

Директовский аудитор видит только факт: счётчик привязан, цели заданы. Здесь становится
видно, **работают ли они**. Типичная связка: в Директе стратегия оптимизируется по цели,
которая в Метрике не срабатывала ни разу — формально всё настроено, фактически стратегия
учится на пустоте.
