# Комбинаторные объявления в API: RESPONSIVE_AD и версия v501

**Правило: если объявление комбинаторное — работать через `ResponsiveAd` и endpoint `v501`.** Путь через `TextAd` в `v5` формально отвечает, но врёт при чтении и отказывает при записи.

## Что это

Комбинаторное объявление (несколько заголовков, текстов, изображений, из которых Директ сам собирает комбинации) в API называется **`RESPONSIVE_AD`**. С июля 2026 такие объявления используются в Единых перфоманс-кампаниях вместо текстово-графических.

Полный список типов в `Type`: TEXT_AD, SMART_AD, MOBILE_APP_AD, DYNAMIC_TEXT_AD, IMAGE_AD, CPC_VIDEO_AD, CPM_BANNER_AD, CPM_VIDEO_AD, SHOPPING_AD, LISTING_AD, **RESPONSIVE_AD**.

## Версии endpoint

| Операция | v5 | v501 |
|---|---|---|
| `get` с `ResponsiveAdFieldNames` | работает | работает |
| `update` с `ResponsiveAd` | **ошибка 3500** «Объявление данного типа не поддерживается в v5, используйте v501» | работает |
| `update` с `TextAd` у комбинаторного | проходит, но с предупреждением **10252** «Комбинаторный баннер изменён через устаревший API текстовых баннеров» | — |

```
https://api.direct.yandex.com/json/v5/ads     ← только чтение комбинаторных
https://api.direct.yandex.com/json/v501/ads   ← чтение и запись
```

## Ловушка при чтении через TextAdFieldNames

Один и тот же объект отдаётся по-разному в зависимости от запрошенных полей:

- запросили `TextAdFieldNames` → `"Type": "TEXT_AD"`, объект `TextAd` с **одним** `Title` и **одним** `Text`;
- запросили `ResponsiveAdFieldNames` → `"Type": "RESPONSIVE_AD"`, объект `ResponsiveAd` с массивами `Titles[]` и `Texts[]`.

То есть через `TextAd` видно только первый заголовок и первый текст — остальная комбинаторика скрыта. Для ссылок разницы нет, для аудита текстов — критично: легко решить, что у объявления один заголовок, и затереть остальные.

## Поля ResponsiveAd

Точный перечень, который принимает `ResponsiveAdFieldNames` (выдан самим API в тексте ошибки при неверном значении):

```
AdImages, DisplayDomain, Href, FinalUrl, SitelinkSetId, Texts, Titles,
DisplayUrlPath, DutPrefix, DutSuffix, SitelinksModeration, AdExtensions,
DisplayUrlPathModeration, PriceExtension, VideoExtensions,
ButtonExtensionModeration, BusinessId, TrackingPhoneId, ButtonExtension,
ErirAdDescription, TrackingParams, Carousel
```

Обратите внимание: `Titles` и `Texts` — массивы объектов вида `{"Title": "...", "Status": "ACCEPTED"}`. Поля `Title2` у комбинаторных нет.

## Рецепт: массовая замена ссылок

```bash
# 1. Прочитать текущее состояние (v5 или v501)
curl -s -X POST https://api.direct.yandex.com/json/v501/ads \
  -H "Authorization: Bearer $TOKEN" -H "Client-Login: $LOGIN" \
  -H "Content-Type: application/json; charset=utf-8" \
  -d '{"method":"get","params":{
        "SelectionCriteria":{"CampaignIds":[123456],"States":["ON","SUSPENDED","OFF"]},
        "FieldNames":["Id","CampaignId","AdGroupId","Type","State"],
        "ResponsiveAdFieldNames":["Href","Titles","Texts"],
        "Page":{"Limit":1000}}}'

# 2. Обновить только Href, сохранив UTM-хвост каждого объявления
curl -s -X POST https://api.direct.yandex.com/json/v501/ads \
  -H "Authorization: Bearer $TOKEN" -H "Client-Login: $LOGIN" \
  -H "Content-Type: application/json; charset=utf-8" \
  -d '{"method":"update","params":{"Ads":[
        {"Id":10000000001,"ResponsiveAd":{"Href":"https://site.ru/page?utm..."}}]}}'
```

Передавать в `update` только изменяемые поля — остальные остаются как были. Батчи до 1000 объектов за вызов; на практике удобнее по 200.

## Лимиты, о которые ломается XLS

**В одной группе допустимо до 3 неархивных комбинаторных объявлений и до 10 с учётом архивных.**

Отсюда следствие, которое стоит знать заранее: **выгрузку кампании с комбинаторными объявлениями часто невозможно загрузить обратно через XLS**. Директ проверяет лимит на весь файл, а в старых кампаниях групп с 9–16 объявлениями сколько угодно — они создавались до введения лимита. Ошибки при загрузке:

```
Строка N: В одной группе не может быть более 3 баннеров типа комбинаторное
Строка N: В одной группе не может быть более 10 архивных баннеров типа комбинаторное
```

Правкой файла это не обходится — ни включением архивных в выгрузку, ни удалением лишних строк. **Для таких кампаний массовые правки делать только через API.**

## Лимиты элементов в одном комбинаторном объявлении

| Элемент | Лимит | Поле на запись |
|---|---|---|
| Заголовки | 7, до 56 символов | `Titles` |
| Тексты | 3, до 81 символа | `Texts` |
| Изображения | 5 | `AdImageHashes` |
| Видео | 6 | `VideoExtensionIds` |

## Форматы записи: не совпадают с форматом чтения

Главная ловушка. То, что вернул `get`, нельзя отправить в `update` как есть.

| Поле | `get` возвращает | `update`/`add` принимает |
|---|---|---|
| Titles | `[{"Title":"...","Status":"ACCEPTED"}]` | `["...", "..."]` — массив строк |
| Texts | `[{"Text":"...","Status":"..."}]` | `["...", "..."]` — массив строк |
| Изображения | `AdImages: {"Items":[{"ImageHash":"...","ImageUrl":"...","Status":"..."}]}` | `AdImageHashes: {"Items":["хеш1","хеш2"]}` |
| Видео | `VideoExtensions: {"Items":[{"CreativeId":123,"RatioType":"HORIZONTAL"}]}` | `VideoExtensionIds` — идентификаторы креативов |

Перебор вариантов для изображений (все, кроме последнего, дают ошибку):

```
"AdImages": [...]                      → «неизвестный параметр ResponsiveAd.AdImages»
"AdImageHashes": ["хеш1","хеш2"]       → «AdImageHashes не может содержать массив»
"AdImageHashes": "хеш"                 → «Некорректное значение для AdImageHashes»
"AdImageHashes": {"Items": ["хеш1"]}   → работает
```

Для заголовков наоборот: объекты `{"Title": "..."}` дают «Элемент массива Titles должен содержать строку» — нужен голый массив строк.

## Приём: схлопывание клонов в одно комбинаторное объявление

Типичная ситуация в старых аккаунтах: Директ конвертировал текстово-графические объявления в `RESPONSIVE_AD`, но у каждого остался один заголовок и один текст. Вместо комбинаторики — десятки клонов в группе, из которых система не может собирать варианты.

**Ограничение, которое мешает в лоб:** добавить новое объявление (`add`) в такую группу нельзя — упрётся в лимит 3 неархивных и 10 с архивными:

```
7001 Достигнуто максимальное количество комбинаторных объявлений в группе - 3
7001 Достигнуто максимальное количество комбинаторных объявлений в группе - 10
```

**Обход:** не создавать новое объявление, а *отредактировать существующее*. `update` не создаёт объект, поэтому лимит на количество не проверяется. Одно объявление становится носителем всех элементов, остальные останавливаются через `suspend`.

Алгоритм:

1. Прочитать активные объявления группы (`States: ["ON"]`).
2. **Разбить по посадочной странице**: группировать по `(AdGroupId, Href без UTM)`. Схлопывать объявления с разными URL нельзя — половина заголовков будет вести не туда.
3. Выбрать носителя — объявление с лучшей статистикой (конверсии → клики → показы), чтобы сохранить накопленную историю.
4. Собрать уникальные заголовки, тексты и хеши изображений всех объявлений подгруппы, отсортировав доноров по эффективности: при превышении лимита отсечётся наименее результативное.
5. `update` носителя, `suspend` остальных.

**Модерация не сбрасывается**: элементы, уже прошедшие проверку в аккаунте, получают `ACCEPTED` сразу, объявление продолжает показы. Ни паузы, ни потери статистики — Id носителя сохраняется.

**Что не переносится само.** `update` меняет только переданные поля, остальные остаются как были. Значит при схлопывании изображения нужно собирать и передавать **явно** — иначе у носителя останется только его собственная картинка, а креативы остановленных объявлений уйдут из показов. Для РСЯ это критично: там объявления часто различаются именно картинками, а не текстами.

Практика на аккаунте с ~500 объявлениями: сеть и ретаргетинг схлопнулись с 156 объявлений до 24, при этом все 25 уникальных изображений сохранены — по 2–5 в каждом носителе вместо одного.

**Откат** возможен всегда: остановленные объявления не удаляются, их можно вернуть в работу, а носителю — восстановить исходный состав элементов из бэкапа `get`, снятого перед правкой.

## Проверено

Август 2026 на боевом аккаунте: чтение через оба варианта полей, `update` в v5 (предупреждение 10252) и в v501 (чисто), лимиты подтверждены отказом XLS-загрузки и ошибками 7001 при `add`, форматы записи заголовков, текстов и изображений — перебором до успешного ответа.
